Privacidade e Segurança

Autenticação OAuth, JWT e Segurança contra XSS/CSRF

Feito por João Pedro Soares da Rosa

RA: 0030482511029 — FATEC Sorocaba José Crespo Gonzales

Introdução

A segurança e a privacidade de dados são pilares fundamentais no desenvolvimento de APIs na atualidade, garantindo que apenas usuários autorizados acessem recursos sensíveis e que as informações transmitidas permaneçam íntegras. Para alcançar esse objetivo, desenvolvedores de software utilizam uma combinação de protocolos de autorização, tokens de autenticação e estratégias de defesa contra ataques comuns na web.

Este trabalho aborda as principais práticas modernas de segurança em APIs: o protocolo OAuth2 (e suas evoluções com PKCE e a especificação OAuth 2.1), o padrão JSON Web Token (JWT) para autenticação sem estado, e as defesas contra os ataques de Cross-Site Scripting (XSS) e Cross-Site Request Forgery (CSRF).

Autenticação e Autorização com OAuth2

O OAuth2 é o padrão de mercado para autorização. Ele permite que uma aplicação acesse recursos em nome de um usuário sem que este precise compartilhar suas credenciais (como senha) diretamente com o serviço de terceiros.

Fluxo de Funcionamento

O OAuth2 define papéis específicos — Dono do Recurso, Cliente, Servidor de Autorização e Servidor de Recursos — e utiliza scopes para limitar o que cada aplicação pode fazer.

Importância

É essencial para ecossistemas de APIs onde a interoperabilidade entre diferentes serviços é necessária de forma segura.

OAuth 2.1 e PKCE

O OAuth continua evoluindo. Em janeiro de 2025, a IETF publicou a RFC 9700 (Best Current Practice for OAuth 2.0 Security), consolidando mais de uma década de aprendizados sobre falhas de implementação. Essas recomendações estão sendo formalizadas na especificação OAuth 2.1, que traz mudanças relevantes:

  • PKCE obrigatório: o Proof Key for Code Exchange (RFC 7636), antes recomendado apenas para clientes públicos (SPAs, apps mobile), passa a ser exigido também para clientes confidenciais no fluxo de Authorization Code. O cliente gera um code_verifier aleatório, deriva dele um code_challenge (via SHA-256) e envia na requisição de autorização. Na troca do código pelo token, precisa apresentar o verificador original. Isso protege contra interceptação e reuso do código de autorização (authorization code injection).
  • Fim do fluxo Implícito (Implicit Grant): os tokens não devem mais trafegar diretamente na URL do navegador, pois ficam expostos em históricos, logs e cabeçalhos Referer.
  • Tokens de curta duração com rotação: access tokens com vida útil curta (tipicamente 15–30 minutos) combinados com refresh tokens que são invalidados e substituídos a cada uso (rotação), reduzindo a janela de exploração em caso de vazamento.
  • Tokens vinculados ao remetente (sender-constrained tokens): técnicas como mTLS ou DPoP amarram o token em quem o solicitou, tornando um token roubado inútil para terceiros.
  • Validação estrita de redirect_uri (correspondência exata, sem wildcards) e uso do parâmetro state para mitigar CSRF durante o fluxo de autorização.

Essas práticas são especialmente relevantes hoje porque uma parcela significativa dos incidentes de segurança em aplicações SaaS está associada a implementações falhas ou incompletas de OAuth.

JSON Web Token (JWT)

O JWT é um padrão (RFC 7519) utilizado para transmitir informações de forma segura entre as partes como um objeto JSON.

  • Estrutura: É composto por três partes: Header (algoritmo e tipo), Payload (dados do usuário ou claims) e Signature (garante que o token não foi alterado).
  • Vantagens: Por ser autossuficiente e compacto, é ideal para autenticação sem estado (stateless), eliminando a necessidade de consultar o banco de dados em cada requisição. Porém, sua segurança depende da força da chave secreta e de como ele é armazenado no cliente.

Algoritmos de assinatura e ataques clássicos

A escolha e a validação do algoritmo são pontos críticos de segurança:

  • Simétrico (HS256): usa uma única chave secreta compartilhada tanto para assinar quanto para validar o token. Qualquer serviço capaz de validar também é capaz de emitir novos tokens, o que é arriscado em arquiteturas com múltiplos microsserviços.
  • Assimétrico (RS256, ES256, EdDSA): usa um par de chaves; a chave privada assina o token e apenas a chave pública é necessária para validá-lo. Isso impede que serviços "consumidores" forjem tokens, pois eles nunca têm acesso à chave privada.
  • Ataque alg: none: a RFC 7519 prevê none como valor válido para tokens não assinados. Bibliotecas mal configuradas que confiam no algoritmo informado no próprio cabeçalho do token permitem que um atacante altere o payload, troque o alg para none, remova a assinatura e envie um token forjado (por exemplo, alterando role: user para role: admin).
  • Confusão de algoritmo (RS256 → HS256): quando o servidor aceita mais de um algoritmo, um atacante pode obter a chave pública RSA (frequentemente exposta em endpoints como /.well-known/jwks.json) e usá-la como se fosse o segredo HMAC para assinar um token falso com HS256. Como o servidor usa a mesma chave pública para validar, a assinatura "bate".
  • Mitigação: nunca confiar no alg informado pelo token. O servidor deve fixar/whitelistar explicitamente o algoritmo esperado (ex.: aceitar somente ["RS256"]), usar segredos HMAC fortes (mínimo de 32 bytes aleatórios quando HS256 for inevitável), validar sempre as claims exp, iss e aud, manter bibliotecas JWT atualizadas e monitorar CVEs conhecidas dessas bibliotecas.

Proteção contra XSS (Cross-Site Scripting)

O XSS ocorre quando um invasor consegue injetar scripts maliciosos em páginas web visualizadas por outros usuários.

  • Impacto no JWT: Se um JWT for armazenado no localStorage do navegador, ele fica vulnerável a ataques XSS, pois qualquer script JavaScript na página pode lê-lo e roubá-lo.
  • Prevenção: As melhores práticas incluem a sanitização de entradas, o uso de Content Security Policy (CSP) e o armazenamento de tokens sensíveis em cookies com a flag HttpOnly, que impede o acesso via JavaScript.

Reforçando a defesa contra XSS

  • Content Security Policy (CSP) na prática: diretivas como script-src 'self' restringem quais origens podem executar scripts, bloqueando a maioria dos payloads XSS injetados por terceiros; o uso de nonces ou hashes (script-src 'nonce-xyz') permite liberar apenas scripts explicitamente autorizados pelo servidor a cada requisição.
  • Sanitização e escaping de saída: além de sanitizar entradas, é fundamental escapar corretamente qualquer dado do usuário renderizado no HTML, evitando usar innerHTML/dangerouslySetInnerHTML com conteúdo não confiável. Frameworks modernos (React, Vue, Angular) já escapam por padrão, mas podem ser burlados se contornar essa proteção manualmente.
  • Cookies de sessão/token com atributos combinados: HttpOnly (bloqueia leitura via JS) + Secure (só trafega em HTTPS) + SameSite (limita envio entre domínios) formam, juntos, uma defesa em camadas mais robusta.

Proteção contra CSRF (Cross-Site Request Forgery)

O CSRF é um ataque que engana um usuário autenticado para que ele execute ações indesejadas em uma aplicação na qual ele já possui uma sessão ativa.

  • O Dilema do Armazenamento: Embora cookies com HttpOnly protejam contra XSS, eles tornam a aplicação vulnerável ao CSRF, pois o navegador envia automaticamente os cookies em requisições para o domínio de origem.
  • Prevenção: Para mitigar esse risco, utiliza-se a estratégia de Tokens Anti-CSRF (um valor único enviado em cada requisição), o atributo SameSite nos cookies e a validação de cabeçalhos personalizados em APIs.

Detalhando o atributo SameSite

O atributo SameSite de um cookie controla se ele é enviado em requisições de origem cruzada (cross-site), e possui três valores possíveis:

  • Strict: o cookie nunca é enviado em navegação vinda de outro site, a proteção mais forte, mas pode quebrar fluxos legítimos (ex.: clicar em um link externo que leva a uma página autenticada).
  • Lax (padrão em navegadores modernos): o cookie é enviado em navegações de nível superior do tipo GET vindas de outro site (como clicar em um link), mas não em requisições POST/PUT/DELETE disparadas por formulários ou scripts de terceiros — bom equilíbrio entre segurança e usabilidade.
  • None: o cookie é sempre enviado entre sites, exigindo obrigatoriamente o atributo Secure (HTTPS); usado quando a aplicação depende de cenários legítimos de cross-site (ex.: widgets embutidos, single sign-on entre domínios).

Camadas complementares de proteção

  • Padrão Double Submit Cookie ou Synchronizer Token Pattern: o servidor gera um token CSRF único por sessão (ou por requisição), que deve ser enviado tanto em um cookie quanto em um cabeçalho/campo de formulário; a requisição só é aceita se os dois valores coincidirem, algo que um atacante externo não consegue reproduzir.
  • Validação do cabeçalho Origin/Referer: APIs podem validar se a requisição realmente partiu do domínio esperado, como camada adicional (não deve ser a única defesa, pois esses cabeçalhos podem ser omitidos em certos cenários legítimos).
  • Rate limiting e MFA (autenticação multifator): mesmo não sendo específicos de CSRF/XSS, limitar tentativas de requisições sensíveis e exigir um segundo fator de autenticação reduzem o impacto de credenciais ou tokens comprometidos por qualquer um dos vetores anteriores.

Conclusão

Uma arquitetura segura trabalha mais como uma estratégia em camadas. O OAuth e o JWT lidam com quem o usuário é e o que ele pode fazer, cada vez mais reforçados por práticas como PKCE, rotação de tokens e validação estrita de algoritmos de assinatura. As defesas contra XSS e CSRF garantem que o canal de comunicação e o ambiente do navegador permaneçam protegidos contra manipulações externas.

A combinação dessas camadas (CSP, cookies HttpOnly/Secure/SameSite, tokens anti-CSRF, PKCE, allowlist de algoritmos JWT, MFA e monitoramento) é o que efetivamente reduz a superfície de ataque de uma API moderna.
